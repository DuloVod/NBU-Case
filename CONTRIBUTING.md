# Спільна робота

## Зміни та гілки

Перед роботою перевіряйте `git status` і виконуйте `git fetch origin`. Не перезаписуйте незакомічені зміни іншої людини. Окреме завдання робіть у гілці на кшталт `data/update-cpi` або `models/qpm-calibration`, потім відкривайте pull request з описом і перевірками.

Не використовуйте force push у спільні гілки. Нові коміти партнера переглядайте перед інтеграцією. Якщо локальна історія розійшлась, узгодьте злиття або безпечно перебазуйте тільки власні неопубліковані коміти.

## Оновлення даних

1. Зберігайте новий оригінал без редагування клітинок. Для нового інформаційного зрізу використовуйте окрему датовану папку/гілку; не називайте старі результати новим прогнозом.
2. Записуйте джерело, URL, дату завантаження, дату публікації, одиниці, частоту, сезонність, статус «факт/оцінка/прогноз» та визначення показника.
3. Додавайте SHA-256 і точний рядок/аркуш або код серії. Не замінюйте невідоме нулем чи прогнозом НБУ.
4. Не змішуйте кумулятивні показники з квартальними, середні ставки зі ставками на кінець періоду, товари з товарами та послугами.
5. Перебудовуйте числові ряди окремо від оформленого Excel. Якщо XLSX не оновлений, прямо зазначайте його дату.

## Зміни моделей

- Усі моделі мають прогнозувати однакову ціль і оцінюватися на однакових датах.
- Підбір параметрів і перетворення виконуються всередині навчального зрізу. Ретроспективно відомі майбутні факти не є допустимими зовнішніми припущеннями.
- Фіксуйте затримки публікацій і відмінність поточного вінтажу від архівних даних.
- Порівнюйте з незмінною ставкою, зберігайте кожен прогноз, а не лише підсумкову метрику.
- Не обирайте специфікацію за фінальною тестовою помилкою й не приховуйте погані періоди. Нові варіанти перевіряйте окремо або використовуйте вкладену валідацію.
- У QPM відрізняйте припущення, калібровані параметри, оцінені параметри та оцінені приховані стани.

## Перед pull request

```sh
python -m unittest discover -s tests -v
```

При зміні вилучення/перетворення даних також виконайте:

```sh
python tools/rebuild_data.py --check
```

Якщо числові зміни очікувані, поясніть причину та збережіть новий інформаційний зріз; не оновлюйте еталонні файли мовчки лише для проходження тесту.

Опис PR: проблема, зміна поведінки, перевірки, вплив на прогноз. Не комітьте середовища, бібліотеки, ключі, листування, персональні дані респондентів або випадкові файли з Downloads/Desktop.
